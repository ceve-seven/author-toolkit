## 二、微服务模块化设计：标准接口 + 注册表

### 2.1 模块标准接口

每个模块（无论主模块还是审核子模块）必须实现以下标准接口，才能被系统识别和调度：

```python
# 所有模块必须实现的基础接口
class BaseModule:
    """所有模块的抽象基类"""
    
    # === 元数据 ===
    module_id: str          # 唯一标识，如 "character_generator"
    module_name: str        # 人类可读名称
    version: str            # 语义化版本 "1.2.0"
    module_type: ModuleType # GENERATOR | WRITER | REVIEWER | TOOL
    
    # === 生命周期 ===
    async def on_register(self) -> None: ...
    async def on_unregister(self) -> None: ...
    async def health_check(self) -> HealthStatus: ...
    
    # === 依赖声明 ===
    @property
    def dependencies(self) -> List[str]:  # 依赖的其他模块ID
        return []
    
    @property
    def provided_apis(self) -> List[APIDefinition]:  # 本模块提供的API
        return []
    
    # === 配置 ===
    async def configure(self, config: ModuleConfig) -> None: ...
    
    # === 数据库 ===
    @property
    def db_schema(self) -> Optional[DBSchema]:  # 本模块需要的数据库表结构
        return None
    
    @property
    def vector_collections(self) -> List[VectorCollection]:  # 本模块需要的向量集合
        return []
```

### 2.2 三种核心代理类型

```
ModuleType 枚举：

GENERATOR  → 生成代理子池
  负责：从"无"到"有"——凭空创造设定、细纲、伏笔等
  特点：高LLM消耗、低实时性要求、可批量异步
  模块：灵感生成器、主题生成器、世界观生成器、人物生成器、
        势力生成器、物品生成器、大纲生成器、细纲生成器、
        伏笔设计器、分卷生成器

WRITER    → 写作代理子池
  负责：从"有"到"完整"——根据约束文件生成正文
  特点：极高LLM消耗、中等实时性、需上下文连续性
  模块：正文生成器、场景展开器、对话写作器、描写增强器

REVIEWER  → 审核代理子池  (每个主模块配备独立的审核子模块)
  负责：检查、验证、打分
  特点：中等LLM消耗、高实时性、可并行执行
  模块：世界观审核器、人物审核器、关系审核器、弧线审核器、
        势力审核器、伏笔审核器、大纲审核器、细纲审核器、
        正文四层审查器、字数校验器、AI痕迹检测器、
        跨模块一致性审查器
```

### 2.3 模块注册表

模块注册表是系统的服务发现中心。新模块要无缝接入，只需：

1. 实现 `BaseModule` 接口
2. 调用 `registry.register(my_module)`
3. 系统自动发现、分配资源、建立路由

```python
class ModuleRegistry:
    """模块注册表 - 服务发现中心"""
    
    # 已注册模块索引
    modules: Dict[str, BaseModule]
    # API端点 → 模块映射
    api_routes: Dict[str, Tuple[BaseModule, APIDefinition]]
    # 事件订阅关系
    event_subscriptions: Dict[str, List[BaseModule]]
    # 模块依赖图
    dependency_graph: DiGraph
    
    async def register(self, module: BaseModule) -> RegisterResult:
        """
        注册新模块。自动完成：
        1. 版本兼容性检查
        2. 依赖完整性验证（依赖的模块是否存在、版本是否兼容）
        3. API端点注册（未冲突则自动分配）
        4. 数据库schema迁移（如果模块声明了新表）
        5. 向量集合创建（如果模块声明了新的向量集合）
        6. 事件订阅建立
        7. 健康检查
        返回注册结果（成功/失败+原因）
        """
        
    async def unregister(self, module_id: str) -> None:
        """
        注销模块。自动完成：
        1. 检查是否有其他模块依赖本模块 → 阻止注销/警告
        2. 清理API路由
        3. 清理事件订阅
        4. 等待进行中的任务完成
        """
    
    def discover_apis(self, capability: str) -> List[APIDefinition]:
        """按能力发现API"""
    
    def get_reviewer_for(self, module_id: str) -> Optional[BaseModule]:
        """获取某个生成/写作模块对应的审核模块"""
```

### 2.4 新模块无缝接入示例

假设后续要添加「读者反馈分析模块」，只需要：

```python
# 步骤1：实现模块
class ReaderFeedbackAnalyzer(BaseModule):
    module_id = "reader_feedback_analyzer"
    module_name = "读者反馈分析器"
    version = "1.0.0"
    module_type = ModuleType.TOOL
    
    dependencies = ["character_retriever", "chapter_retriever"]  # 依赖已有模块
    
    @property
    def db_schema(self):
        return DBSchema(
            new_tables=[
                Table("reader_feedback", 
                    Column("id", UUID),
                    Column("chapter_id", str),
                    Column("feedback_type", str),
                    Column("content", Text),
                    Column("created_at", Timestamp)
                )
            ],
            new_columns=[
                # 在已有表中添加新字段（不影响原有数据）
                ("chapter_metadata", "reader_sentiment_score", Float)
            ]
        )
    
    @property
    def vector_collections(self):
        return [
            VectorCollection(
                name="reader_feedback_vectors",
                dimension=1024,
                metadata_schema={"chapter_id": str, "feedback_type": str}
            )
        ]

# 步骤2：注册（一行代码，其他全自动）
await registry.register(ReaderFeedbackAnalyzer())
# → 自动建表、创建向量集合、注册API路由、建立依赖关系 ✅
# → 原有所有模块不受任何影响 ✅
```

关键在于：新模块的数据库变更通过**增量迁移**实现——新增表不影响已有表，新增列有默认值。系统在注册时自动运行迁移脚本。

## 三、子代理分离：生成/写作/审核三池独立

### 3.1 为什么要分离

| 维度 | 不分离的问题 | 分离后的方案 |
|------|------------|------------|
| LLM 调用策略 | 生成、写作、审核共用同一个LLM调用策略 | 生成用高温度（创意），写作用中温度（稳定），审核用低温度（精确） |
| 上下文管理 | 审核消耗大量token扫描全文，挤占写作的上下文空间 | 审核在独立上下文中运行，不影响写作代理的章节连续性 |
| 并发控制 | 无法同时进行下一章的生成和上一章的审核 | 三个代理池独立调度，真正的流水线并行 |
| 故障隔离 | 审核出bug卡住了，整个系统停止 | 审核故障不影响生成和写作继续 |
| 资源分配 | 无法为审核分配独立GPU/内存 | 审核代理可部署到低成本节点 |

### 3.2 子代理通信协议

子代理之间不直接调用，而是通过消息队列异步通信：

```
═══════════════════════════════════════════════════════════════
消息类型定义
═══════════════════════════════════════════════════════════════

GENERATE_REQUEST (生成任务)
  → 发布者：用户 / 细纲代理 / 大纲代理
  → 消费者：生成代理池
  示例：
  {
    "task_id": "gen-20260528-001",
    "task_type": "character_generation",
    "payload": {
      "novel_id": "novel-001",
      "spec": "创建一个复仇型主角，背景为末世..."
    },
    "callback_queue": "orchestrator.callback"
  }

WRITE_REQUEST (写作任务)
  → 发布者：用户 / 生成代理
  → 消费者：写作代理池
  示例：
  {
    "task_id": "write-20260528-028",
    "task_type": "chapter_writing",
    "payload": {
      "novel_id": "novel-001",
      "chapter_id": "CH-028",
      "constraints_file": "manuscript/CH-028/constraints.json",
      "scene_index": 2
    },
    "callback_queue": "orchestrator.callback"
  }

REVIEW_REQUEST (审核任务)
  → 发布者：生成代理 / 写作代理 / 用户
  → 消费者：审核代理池
  示例：
  {
    "task_id": "review-20260528-028",
    "review_layers": ["consistency", "logic", "literary", "reader_engagement"],
    "payload": {
      "novel_id": "novel-001",
      "target_type": "chapter",
      "target_id": "CH-028",
      "draft_version": "draft_v1"
    },
    "callback_queue": "orchestrator.callback"
  }

SYNC_EVENT (数据变更事件)
  → 发布者：任何修改了数据库的代理
  → 消费者：同步引擎、缓存更新器、Markdown渲染器
  示例：
  {
    "event_type": "entity_updated",
    "entity_type": "character",
    "entity_id": "CHAR-001",
    "changed_fields": ["faction_id", "core_desire"],
    "old_values": {"faction_id": "FAC-003"},
    "new_values": {"faction_id": "FAC-005"},
    "triggered_by": "user_manual_edit"
  }
```

### 3.3 流水线并行示例

用户请求「生成第28章并审核」的完整调度链：

```
时间轴 ────────────────────────────────────────────────────────►

生成代理池:
  [准备29章细纲约束] ────────────────────────────►
                          
写作代理池:
  [生成28章场景一] [生成28章场景二] [生成28章场景三] ──►
                              │
审核代理池:                   │
  [审核28章场景一](并行)      │
       [审核28章场景二](并行)  │
                [审核28章场景三](并行)
                         [跨场景一致性审核]
                              │
同步引擎:                     │
  [更新CHAR/ITEM/FORE状态] ◄──┘
  [渲染Markdown文件]
  [更新向量索引]

总耗时 ≈ max(场景生成) + max(场景审核) + 同步
       ≈ 不再是 ∑所有步骤 的串行时间
```

## 五、向量搜索：语义检索能力

### 5.1 为什么需要向量搜索

关键词匹配在小说创作中有致命局限：

```
用户查询：「找所有和主角有过不愉快经历但在第25章之后关系缓和的人物」

关键词匹配的做法：
  搜索「不愉快」→ 0结果
  搜索「关系缓和」→ 0结果  
  搜索「冲突」→ 返回所有有冲突的角色（噪音巨大）

向量搜索的做法：
  将查询编码为向量 → 在角色关系的语义空间中找最近邻
  → 返回 REL-003（与CHAR-003：冲突后和解）
  → 返回 REL-007（与CHAR-006：误解消除）
  → 附带相似度分数和来源引用
```

### 5.2 向量化方案

```
═══════════════════════════════════════════════
向量化对象 & 嵌入策略
═══════════════════════════════════════════════

1. 角色档案向量 (character_profile_vectors)
   维度：1024
   嵌入内容：CHAR档案的聚合文本
     = char_name + core_desire + deep_need + core_fear + 
       perception_filter + status_timeline_summary
   元数据：{char_id, faction_id, weight_tier, arc_stage}
   用途：
     - "找和CHAR-001内心矛盾最相似的角色"
     - "所有处于弧线变化节点区间的角色"

2. 章节正文向量 (chapter_content_vectors)  
   维度：1024
   嵌入方式：分块嵌入（每章分成约500字的块，每个块独立向量化）
   嵌入内容：章节正文
   元数据：{chapter_number, chunk_index, char_ids_present, scene_type}
   用途：
     - "找所有描写过类似场景氛围的段落"
     - "CHAR-001上次表现出恐惧是什么场景"

3. 伏笔描述向量 (foreshadow_vectors)
   维度：1024
   嵌入内容：payload + surface + plant_form + reveal_form
   元数据：{fore_id, status, depth, tags}
   用途：
     - "有没有和这个新伏笔内容相似的已有伏笔"（防重复）
     - "所有关于'信任'主题的伏笔"

4. 世界观规则向量 (world_rule_vectors)
   维度：1024
   嵌入内容：rule_name + description + cost + limitation
   元数据：{rule_id, category}
   用途：
     - "这个情节设计可能违反哪些规则"
     - "所有涉及'代价'概念的规则"

5. 主题陈述向量 (theme_vectors)
   维度：1024
   嵌入内容：theme_statement（各卷映射版本也分别向量化）
   元数据：{novel_id, volume_number}
   用途：
     - "第28章的内容偏离了主题吗"（计算章节向量与主题向量的余弦相似度）
═══════════════════════════════════════════════
```

### 5.3 嵌入模型选择

```
开发环境推荐：
  → bge-large-zh-v1.5 (BAAI)   | 1024维 | 中文优化 | 本地部署
  → m3e-base (Moka AI)          | 768维  | 中文优化 | 轻量快速

生产环境推荐：
  → text-embedding-3-large (OpenAI) | 3072维 | 多语言 | 云端API
  → 或继续使用 bge-large-zh   | 本地可控 | 无API费用

向量数据库推荐：
  → Chroma (开发)  | 轻量、Python原生、零配置
  → Milvus (生产)  | 分布式、十亿级向量、混合搜索
  → pgvector (折中) | PostgreSQL扩展、无需额外部署、与关系型数据库统一
```

## 八、总结：本次升级解决了什么

| 问题 | 升级前 | 升级后 |
|------|--------|--------|
| 模块扩展 | 需手动修改核心代码、更新索引逻辑 | 实现 `BaseModule` 接口 → 一行 `registry.register()` → 自动发现、建表、注册路由 |
| 审核模块 | 审核逻辑耦合在主模块中 | 每个主模块配备独立审核子模块，`registry.get_reviewer_for(module_id)` 自动绑定 |
| 生成 vs 写作 | 同一代理执行，上下文混杂 | 三个独立代理池：Generator（创意/高温度）、Writer（稳定/中温度）、Reviewer（精确/低温度） |
| 数据存储 | JSON 文件，大数量时查询困难 | PostgreSQL 关系型数据库，索引加速，结构化查询 |
| 语义检索 | 仅关键词匹配 | pgvector 向量搜索 + 混合检索（向量+关键词+元数据过滤） |
| 联动更新 | 遍历所有JSON文件查找引用 | `entity_references` 表一次JOIN查询 |
| 变更追踪 | 分散在各JSON的`modification_history`字段 | 统一的 `change_log` 表，按时间、实体、字段三维查询 |

这是一个从「单体JSON脚本」到「微服务数据库系统」的完整架构升级。核心思想不变——用户只看中文 Markdown，AI 只操作结构化数据——但底层从一个文件系统变成了一个可扩展的、可并行的、可搜索的服务集群。
