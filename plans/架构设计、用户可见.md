这是一个决定性架构决策。如果用户只能通过AI间接接触自己的设定，那这套系统就是黑箱——用户的信任会在第三次「AI你给我看看CHAR-001现在的完整档案」时崩塌。必须让用户能直接看到、直接修改自己的小说数据。

下面设计双层架构：**系统引擎层（英文）+ 用户可视层（中文Markdown）+ 双向同步引擎**。

## 四、双向同步引擎

### 4.1 同步方向与触发条件

```
═══════════════════════════════════════════════════
方向一：用户修改Markdown → 同步到JSON
═══════════════════════════════════════════════════
触发条件：用户保存了Markdown文件（或文件变更被检测到）
同步引擎行为：
  1. 扫描文件中的所有 SYNC 标记
  2. 提取标记内的当前内容
  3. 与上一次同步时的内容比对
  4. 识别变更字段
  5. 更新对应JSON文件中的对应字段
  6. 递增JSON的version号
  7. 追加change_log记录
  8. 更新SYNC_META中的last_modified

═══════════════════════════════════════════════════
方向二：AI修改JSON → 同步到Markdown
═══════════════════════════════════════════════════
触发条件：AI通过任何操作修改了JSON文件中的字段
同步引擎行为：
  1. 识别被修改的JSON字段
  2. 定位对应Markdown文件中的对应SYNC标记
  3. 替换标记内的内容为新值
  4. 更新Markdown中的SYNC_META（版本号、修改时间）
  5. 如果是新增实体 → 基于模板创建新的Markdown文件
  6. 如果是删除实体 → 在Markdown文件名前加「_已删除_」前缀并添加删除说明
```

### 4.2 字段路径映射规则

JSON字段路径到Markdown SYNC标记的映射是固定的：

```
JSON路径                            → Markdown SYNC标记
─────────────────────────────────────────────────────────
CHAR-001.fields.name                → <!-- SYNC:CHAR-001:fields.name -->
CHAR-001.fields.core_desire         → <!-- SYNC:CHAR-001:fields.core_desire -->
CHAR-001.fields.voice_fingerprint.
  sentence_preference               → <!-- SYNC:CHAR-001:fields.voice_fingerprint.sentence_preference -->
CHAR-001.fields.knowledge_boundary  → <!-- SYNC:CHAR-001:fields.knowledge_boundary -->
CHAR-001.last_modified              → <!-- SYNC_META:CHAR-001:last_modified -->
```

映射规则：`<!-- SYNC:实体ID:JSON字段路径（用.分隔） -->`

### 4.3 冲突处理

当用户在Markdown中修改了某字段，同时AI在JSON中也修改了同一字段时：

```
冲突检测：同步引擎比对 Markdown 和 JSON 的 last_modified 时间戳。

情况一：Markdown 的 last_modified > JSON 的 last_modified
  → 以 Markdown 为准（用户手动修改优先）
  → 将 Markdown 内容同步到 JSON

情况二：JSON 的 last_modified > Markdown 的 last_modified
  → 以 JSON 为准（AI修改优先）
  → 将 JSON 内容同步到 Markdown

情况三：两者 time 相同或无法判断（罕见）
  → 保留两份内容，生成冲突报告，通知用户手动裁决

冲突报告格式：
  ⚠️ 同步冲突：CHAR-001.fields.core_desire
  Markdown 版本（用户修改于 18:45）：找出当年害死他搭档的幕后指使者。
  JSON 版本（AI 修改于 18:45）：找出真相，无论代价是什么。
  请选择保留哪个版本，或手动合并。
```

### 4.4 新增与删除实体的同步

**新增实体（AI创建）**：

```
1. AI 创建 CHAR-008.json
2. 同步引擎检测到新实体
3. 基于人物档案模板生成 05_人物/CHAR-008_【姓名】.md
4. Markdown 文件自动填充 SYNC 标记和默认内容
5. 更新引用索引（如果有其他实体引用了 CHAR-008）
6. 通知用户：「新人物 CHAR-008 的档案已生成，请在 05_人物/ 中查看并完善。」
```

**删除实体（AI标记删除或用户删除文件）**：

```
用户手动删除 Markdown 文件：
  1. 同步引擎检测到文件删除
  2. 弹窗确认：「是否确认删除 CHAR-008？这将同时删除系统档案和相关引用。」
  3. 用户确认 → 删除对应JSON文件 → 清理所有引用关系 → 生成影响报告

AI 标记删除：
  1. AI 将 JSON 文件状态改为「已删除」
  2. 同步引擎在 Markdown 文件名前加「_已删除_」前缀
  3. 文件内容顶部添加删除说明（删除原因、删除时间、影响范围）
  4. 用户可以在可视文件夹中查看已删除的内容（作为历史参考）
```

## 七、同步引擎的工作流程

### 7.1 启动时

```
1. 同步引擎启动
2. 扫描 user_view/ 中所有 Markdown 文件的 SYNC 标记
3. 比对 Markdown 中的 SYNC_META last_modified 和 JSON 文件中的 last_modified
4. 识别不一致的文件
5. 对每个不一致文件：
   → Markdown 更新 → 同步到 JSON
   → JSON 更新 → 同步到 Markdown
   → 双方都更新且冲突 → 生成冲突报告
6. 输出同步状态报告
```

### 7.2 运行时

```
同步引擎持续运行，监听两端的文件变更：

user_view/ 变更事件 → 
  识别变更的 Markdown 文件和 SYNC 标记 →
  提取新内容 →
  更新 JSON →
  更新 SYNC_META →
  记录 change_log

system/ 变更事件 →
  识别变更的 JSON 文件 →
  定位对应的 Markdown 文件 →
  替换对应 SYNC 标记内的内容 →
  更新 SYNC_META
```

### 7.3 AI 操作时的同步保证

当 AI 通过工具修改 system/ 中的 JSON 文件后，同步引擎自动触发 Markdown 更新。用户打开对应的 Markdown 文件时，看到的就是最新内容。

当用户在编辑器中保存了 Markdown 文件的修改后，同步引擎自动触发 JSON 更新。AI 下次拉取该实体的数据时，读取的就是用户修改后的内容。

## 九、设计总结

| 需求 | 实现方式 |
|------|---------|
| 所有内容用户可视 | user_view/ 目录下所有 Markdown 文件，中文，结构清晰 |
| Markdown 即可 | 所有实体档案、结构、正文都以 Markdown 存储 |
| 全中文 | user_view/ 下的文件名、目录名、文件内容全部中文 |
| 项目架构清晰 | user_view/（用户层）+ system/（系统层）+ sync_engine/（同步层）三层分离 |
| 用户修改后同步 | 文件监听 → 标记解析 → 字段提取 → JSON 更新 → 版本递增 |
| AI 修改后同步 | JSON 变更 → 标记定位 → Markdown 替换 → SYNC_META 更新 |
| 双向实时 | 同步引擎持续运行，任意端变更自动触发另一端更新 |
| 冲突处理 | 基于时间戳判断优先级，双方冲突时生成报告通知用户 |
