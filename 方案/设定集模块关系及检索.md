前面几轮已经把每个模块的独立质量保证讲透了。但模块独立没问题，模块之间的**交叉地带**才是设定不一致的真正高发区。这个问题可以拆成三个子问题：怎么建立统一的数据底层、怎么保证修改时自动追踪连锁反应、怎么在写作时随时精准查到所需内容。

以下是一套完整的整合方案。

## 一、中央档案库：统一的底层数据架构

所有模块的数据不是各自存在独立的文件里，而是存储在同一个**中央档案库**中，通过统一 ID 体系互相引用。

### 1.1 统一 ID 体系

每个实体——无论它属于哪个模块——在创建时自动获得一个唯一 ID。ID 不是随机字符串，而是携带类型信息的结构化编码：

- `CHAR-001`：人物（Character），编号 001
- `FAC-003`：势力（Faction），编号 003
- `ITEM-012`：物品（Item），编号 012
- `LOC-005`：地点（Location），编号 005
- `EVT-008`：关键事件（Event），编号 008
- `RULE-004`：世界观规则（Rule），编号 004

这个 ID 体系的好处是：当你在人物档案里写「CHAR-001 隶属于 FAC-003」，AI 可以自动追踪——FAC-003 被改动了，CHAR-001 是否需要同步更新？不需要用户手动对比，AI 自动完成。

### 1.2 各模块的核心数据结构

每个模块在档案库中存储的不只是文本描述，而是一套**结构化字段**。结构化的目的是让 AI 可以在字段级别追踪一致性，而不是在段落级别猜测。

**人物档案（CHAR）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | CHAR-XXX | 唯一标识 |
| name | string | 姓名/称号 |
| faction_id | FAC-XXX 或 null | 所属势力 |
| items_held | [ITEM-XXX, ...] | 当前持有的物品 |
| arc_id | ARC-XXX | 关联的角色弧线 |
| core_contradiction | string | 核心矛盾（身份 vs 欲望） |
| emotional_body_map | dict | 情感→身体反应映射 |
| voice_fingerprint | dict | 语气指纹（词汇池/句式偏好/禁忌表达） |
| knowledge_boundary | dict | 按章节标注的知识边界 |
| status_timeline | [(章节, 状态描述), ...] | 人物状态的时间线 |

**人物关系档案（REL）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | REL-XXX | 唯一标识 |
| char_a | CHAR-XXX | 关系中的角色 A |
| char_b | CHAR-XXX | 关系中的角色 B |
| public_layer | string | 公开层面关系 |
| actual_layer | string | 实际层面关系 |
| hidden_layer | string | 潜在层面（未爆发） |
| change_curve | [(章节, 关系状态), ...] | 关系变化的时间线 |
| conflict_trigger | string | 这条关系的核心摩擦点 |

**角色弧线档案（ARC）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | ARC-XXX | 唯一标识 |
| char_id | CHAR-XXX | 所属人物 |
| node_start | (章节, 状态) | 起点节点 |
| node_catalyst | (章节, 事件) | 催化节点 |
| node_change | (章节, 转变) | 变化节点 |
| node_end | (章节, 状态) | 终点节点 |
| cost_list | [(代价描述, 付出章节), ...] | 弧线完整的代价清单 |

**势力档案（FAC）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | FAC-XXX | 唯一标识 |
| dna_goal | string | 核心目标 |
| dna_method | string | 核心手段 |
| dna_taboo | string | 核心禁忌 |
| dna_origin | string | 起源 |
| dna_secret | string | 核心秘密 |
| dna_crack | string | 内部裂痕 |
| resources | dict | 资源禀赋 |
| members | [(CHAR-XXX, 角色), ...] | 成员及角色列表 |
| items_controlled | [ITEM-XXX, ...] | 控制的物品 |

**势力关系档案（FAC_REL）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | FAC_REL-XXX | 唯一标识 |
| fac_a | FAC-XXX | 势力 A |
| fac_b | FAC-XXX | 势力 B |
| public_stance | string | 公开立场 |
| actual_stance | string | 实际立场 |
| game_matrix | dict | 博弈矩阵（各方的策略和收益） |
| optimal_strategy | string | 各方的最优策略 |
| hidden_threads | [string, ...] | 暗线（表面下在发生什么） |

**物品档案（ITEM）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | ITEM-XXX | 唯一标识 |
| name | string | 名称 |
| first_appear | 章节编号 | 首次出现 |
| ability | string | 能力/属性描述 |
| limitation | string | 使用限制/代价 |
| holder_timeline | [(章节, CHAR-XXX), ...] | 持有者变化时间线 |
| status_timeline | [(章节, 状态), ...] | 状态变化时间线（完好/损坏/丢失/销毁） |
| related_rules | [RULE-XXX, ...] | 关联的世界观规则 |
| narrative_function | string | 叙事功能（麦高芬/契诃夫之枪/象征物/实用工具） |

### 1.3 引用关系图：谁依赖谁

AI 自动维护一张**模块依赖图**，实时追踪每个实体「被谁引用」和「引用了谁」：

```
CHAR-001（主角）
  ├─ 引用 FAC-003（所属势力）
  ├─ 引用 ARC-001（角色弧线）
  ├─ 持有 ITEM-005, ITEM-012
  ├─ 参与关系 REL-001（与 CHAR-002）
  ├─ 参与关系 REL-003（与 CHAR-004）
  └─ 被大纲 EVT-007, EVT-015 引用

FAC-003（主角所属势力）
  ├─ 成员 CHAR-001, CHAR-005, CHAR-008
  ├─ 控制 ITEM-007, ITEM-009
  ├─ 参与势力关系 FAC_REL-001, FAC_REL-003
  └─ 遵循世界观规则 RULE-002, RULE-005
```

这张图的存在意味着：当 AI 修改 FAC-003 时，不需要用户告诉它「顺便检查一下 CHAR-001 的设定有没有受影响」——AI 顺着依赖图自动追踪，所有被影响的内容都在更新清单里。

## 二、联动更新机制：修一处，自动同步全部

这是模块整合的核心——保证「改了一个地方的设定，其他地方不会变成过时数据」。

### 2.1 触发条件

以下任何操作都会触发联动更新检查：

- 修改任何一个实体的核心字段（比如改了 CHAR-001 的 faction_id）
- 新增一个实体（新人物加入，可能影响势力结构）
- 删除一个实体（人物死亡或离开，影响关系网络和物品持有链）
- 移动大纲中的关键事件位置（影响弧线节点的章节标注）

### 2.2 影响范围自动追踪

AI 在触发条件满足后，不等待用户指令，直接执行影响范围扫描：

**第一步：正向追踪——「这个实体引用了什么？」**
修改 CHAR-001 的 faction_id 从 FAC-003 改为 FAC-005：

- ARC-001（角色弧线）的催化节点是否和原势力 FAC-003 相关？如果相关，催化节点需要重新设计。
- REL-001（与 CHAR-002 的关系）是否建立在「两人同属 FAC-003」这个前提上？如果是，关系基础被改变了，需要重新定义。
- CHAR-001 的 knowledge_boundary 中是否有 FAC-003 专属的内部信息？如果有，角色离开势力后这些知识的获取需要重新安排。

**第二步：反向追踪——「谁引用了这个实体？」**
修改 ITEM-005 的 ability（比如从「可以打开任何锁」改为「只能打开特定类型的锁」）：

- 持有者 CHAR-001 在 EVT-015 中使用 ITEM-005 开锁——这个情节现在是否还成立？如果不成立，需要修改 EVT-015 的解决方案。
- FAC-003 因为控制 ITEM-005 而获得的战略优势——削弱后是否影响势力博弈矩阵？

**第三步：涟漪扩散——「受影响者的受影响者」**
如果 ARC-001 因为 faction_id 的变更而需要修改催化节点，那么：

- EVT-007（催化事件）需要修改
- EVT-007 的修改可能影响它所在章节的节奏曲线
- 如果 EVT-007 也是 REL-003 的一个关键转折点，REL-003 的关系时间线需要同步调整

AI 追踪到涟漪不再产生新的有意义的影响为止。

### 2.3 联动更新报告

AI 完成上述扫描后，生成一份《联动更新报告》，而不是直接修改——让用户审核影响范围后再执行：

```
=== 联动更新报告 ===

触发操作：修改 CHAR-001 的所属势力（FAC-003 → FAC-005）

直接影响：
  [CHAR-001] faction_id 已修改 ✓

需要确认的连锁影响：

1. [ARC-001] 角色弧线催化节点
   原催化节点：CHAR-001 在 FAC-003 的内斗中被背叛。
   问题：CHAR-001 现在属于 FAC-005，原催化节点不再成立。
   建议方案 A：催化改为 FAC-005 的内部危机触发。
   建议方案 B：催化改为 CHAR-001 离开 FAC-003 的过程本身就是催化。
   请选择或提供方向。

2. [REL-001] CHAR-001 与 CHAR-002 的关系
   原关系基础：两人同属 FAC-003，是战友。
   问题：CHAR-001 离开后，这条关系的公开层和实际层都需要重新定义。
   建议：转为「前战友，现分属不同势力」关系，增加冲突维度。
   保留原关系的情感基础但改变结构位置。

3. [EVT-015] 情节节点
   CHAR-001 利用 FAC-003 的内部渠道获取情报——不再成立。
   建议：改为 CHAR-001 通过新势力 FAC-005 的资源获取情报。

请逐条确认后，AI 将执行更新。
```

用户不需要分析依赖关系——AI 已经做完了。用户只需要逐条做判断：「方案 A」「保留但调整」「不做修改」三种决策之一。

### 2.4 版本快照

每次联动更新执行前，AI 自动创建一个版本快照。快照包含当前全部档案的状态。如果更新后发现方向不对，用户一句话回滚：

> 「回滚到修改 faction_id 之前的版本。」

AI 恢复所有被修改的档案到快照状态。不需要用户记住改了什么——AI 记得。

## 三、模块一致性交叉验证

除了联动更新（在修改时触发），还需要定期的一致性交叉验证（用户可以在任何时候触发）。这是一个全局扫描，检查所有模块之间的引用是否仍然成立。

### 3.1 六模块交叉检查矩阵

| 检查对 | 检查内容 |
|--------|---------|
| **人物 ↔ 势力** | 每个人物的 faction_id 指向的势力是否存在？人物的社会身份是否和势力设定一致？ |
| **人物 ↔ 弧线** | 每个人物的 arc_id 是否指向有效的弧线？弧线的阶段节点（起点/催化/变化/终点）是否和人物的 status_timeline 匹配？ |
| **人物 ↔ 物品** | 人物持有的物品是否在物品仓库中有记录？物品的 holder_timeline 是否和人物的持有状态一致？ |
| **人物 ↔ 关系** | 每个人物参与的所有关系是否在关系档案中都有定义？关系的时间线变化是否和大纲中的关键事件对应？ |
| **势力 ↔ 势力关系** | 每个势力对的关系档案是否存在？势力关系的变化是否和大纲中的政治/军事事件对应？ |
| **势力 ↔ 物品** | 势力控制的物品是否在物品仓库中有记录？势力获得/失去物品的时间点是否在物品的 holder_timeline 上有对应？ |
| **物品 ↔ 世界观规则** | 每件物品的 related_rules 是否指向有效的世界观规则？物品的能力和限制是否符合关联规则的约束？ |
| **物品 ↔ 大纲事件** | 每件物品的叙事功能（麦高芬/契诃夫之枪等）在大纲中是否有对应的使用节点？契诃夫之枪是否在后续章节中确实「开火」了？ |
| **弧线 ↔ 大纲节点** | 每条弧线的节点（起点/催化/变化/终点）是否和大纲中的具体事件对应？弧线的代价清单是否在后续情节中被兑现？ |
| **关系 ↔ 弧线** | 核心关系的变化是否反映在参与双方各自的弧线中？关系的转折点是否在弧线的节点上有体现？ |

### 3.2 AI 自动执行交叉验证

用户触发验证时，AI 逐对执行上述检查，输出《交叉验证报告》：

```
=== 交叉验证报告 ===

✅ 人物 ↔ 势力：全部一致
✅ 人物 ↔ 弧线：全部一致
⚠️ 人物 ↔ 物品：2 处不一致
  1. CHAR-003 在档案中持有 ITEM-007，但 ITEM-007 的 holder_timeline 显示
     当前持有者为 CHAR-005。请确认以哪份数据为准。
  2. CHAR-006 在 EVT-022 中使用了 ITEM-011，但 CHAR-006 的 items_held 列表
     中没有 ITEM-011。需要在人物档案中补充。
✅ 势力 ↔ 势力关系：全部一致
⚠️ 物品 ↔ 世界观规则：1 处不一致
  1. ITEM-004 的能力涉及「跨维度传送」，但世界观规则库中不存在关于维度结构
     的规则。需要补充世界观规则，或修改 ITEM-004 的能力描述。
⚠️ 物品 ↔ 大纲事件：1 处不一致
  1. ITEM-008 被标记为「契诃夫之枪」（叙事功能），但在后续大纲中没有找到
     使用节点。需要添加使用节点，或将其叙事功能改为「象征物」。
✅ 弧线 ↔ 大纲节点：全部一致
⚠️ 关系 ↔ 弧线：1 处不一致
  1. REL-005（CHAR-002 与 CHAR-004 的决裂）发生在章节 18，但 CHAR-002 的
     弧线 ARC-002 在章节 18 没有对应的节点标注。需要在弧线中补充。

共检查 10 对交叉关系，5 处不一致。AI 已生成修正方案，请逐条确认后执行。
```

用户可以逐条确认或一次性全部执行修正。

## 四、写作时的智能检索系统

前面解决了「怎么保证设定一致」。另一个问题是「写作时怎么精准找到需要的内容」。当用户写到第 35 章，需要确认「CHAR-004 在这一章应该持有哪些物品」时，不应该去翻原始档案文件。

### 4.1 四种检索模式

**模式一：语义检索——用自然语言找**

用户不需要记住档案中的精确术语。自然语言即可：

> 「找所有和主角有关联但还没翻脸的角色。」

AI 在中央档案库中执行语义搜索，检索 CHAR-001 的所有关系档案（REL），筛选 actual_layer 状态不是「敌对/决裂」的关系，返回对应的角色列表和当前关系状态。

> 「找所有在第三幕中有重要作用的物品。」

AI 检索物品仓库中 narrative_function 为「契诃夫之枪」且使用章节在第三幕范围内的物品。

**模式二：精确查询——结构化条件**

用户给出精确条件，AI 返回匹配结果：

> 「显示 CHAR-003 在当前章节（第 18 章）的知识边界——他知道什么、不知道什么。」

> 「列出 FAC-005 在第 12 章时控制的所有物品。」

> 「CHAR-001 的弧线在第 25 章的阶段状态是什么？他已经过了变化节点吗？」

**模式三：关联展开——中心辐射**

用户指定一个实体，AI 展开它的完整关联网络：

> 「展开 CHAR-002 的完整关联。」

AI 返回：
```
CHAR-002 关联网络：
  所属势力：FAC-004（反对派）
  持有物品：ITEM-003, ITEM-009
  角色弧线：ARC-002（当前阶段：变化中，第 22 章）
  参与关系：
    - REL-001（与 CHAR-001）：公开盟友，实际暗藏猜忌
    - REL-004（与 CHAR-005）：公开敌对，实际有共同利益
    - REL-006（与 CHAR-007）：公开中立，实际师徒
  关键事件：
    - EVT-012（第 12 章）：CHAR-002 做出关键选择
    - EVT-023（第 23 章）：CHAR-002 的转折点（未到来）
```

**模式四：写作时的即时上下文提示**

用户不需要主动检索。当用户开始写正文时，AI 自动提示当前章节相关的设定：

> 用户：「开始写第 28 章。」

AI 自动提取并在侧栏显示：

```
📋 第 28 章上下文速览

当前章节关键人物：
  CHAR-001（主角）——弧线阶段：变化中，已付出代价 X，尚未获得 Y
  CHAR-003（盟友）——知识边界：不知道 FAC-005 的秘密
  CHAR-006（对手）——持有 ITEM-011，能力最近升级

当前章节关键物品状态：
  ITEM-005——当前持有者 CHAR-001，状态：部分损坏（自第 24 章起）
  ITEM-012——当前持有者 CHAR-003，状态：完好

当前章节势力格局：
  FAC-003 与 FAC-005——公开联盟，实际 FAC-005 准备背刺（第 30 章）
  FAC-004——暂时中立，观望中

本章需推进的伏笔：
  VF-007（CHAR-001 的隐藏身份线索）——本章需要给一个暗示
  VF-012（ITEM-005 的真正来源）——暂不需要推进，到第 32 章
```

这个上下文速览让用户不需要离开写作界面去查任何东西。AI 已经把当前章节需要的全部信息提取好了。

### 4.2 检索的交互设计

检索不需要用户切换到独立的检索界面。用户在写作过程中随时用自然语言提问，AI 即时返回结果——就像和一个熟悉整个设定集的助理对话：

> 「对了，CHAR-004 在这一章里和 CHAR-001 的关系发展到哪一步了？我不记得他们上次见面时的状态了。」

AI：根据关系档案 REL-003，CHAR-001 与 CHAR-004 的上次关键交互在第 21 章，当时 CHAR-004 发现了 CHAR-001 隐瞒的一个事实，目前关系处于「表面维持合作，实际 CHAR-004 已经开始独立调查」的状态。在本章（第 28 章）的时间线上，他们尚未再次见面。

> 「ITEM-007 现在在谁手里？状态是什么？」

AI：ITEM-007 当前持有者 FAC-005（非个人持有，由势力控制），状态完好。上一任个人持有者是 CHAR-007，在第 19 章交给了 FAC-005。CHAR-007 的弧线中这个交出行为标记为代价节点。

## 五、整合后的完整工作流

将以上设计整合进创作流程中：

### 5.1 初始创建阶段

AI 按顺序创建各模块内容，每创建一个实体就自动分配 ID、建立引用关系。创建顺序：

1. 世界观规则（RULE）——底层约束，最先创建
2. 势力（FAC）——在世界观约束下建立
3. 势力关系（FAC_REL）——势力创建完成后建立博弈矩阵
4. 人物（CHAR）——关联到势力，引用世界观规则
5. 物品（ITEM）——关联到世界观规则，标注叙事功能
6. 人物关系（REL）——人物创建完成后建立关系对
7. 角色弧线（ARC）——基于人物和大纲节点建立

这个顺序确保了每个模块创建时，它引用的其他模块已经存在——不会出现「CHAR-001 引用 FAC-005，但 FAC-005 还没创建」的情况。

### 5.2 修改迭代阶段

任何修改触发联动更新流程：

```
用户提出修改
    ↓
AI 执行修改
    ↓
AI 自动扫描依赖图，追踪影响范围
    ↓
AI 生成《联动更新报告》
    ↓
用户逐条审核（确认/调整/拒绝）
    ↓
AI 执行批准的更新
    ↓
AI 创建版本快照
    ↓
AI 输出《更新摘要》
```

### 5.3 写作执行阶段

用户开始写某一章的正文时：

```
用户：「开始写第 N 章」
    ↓
AI 自动输出《第 N 章上下文速览》
    ↓
用户开始写作
    ↓
用户随时自然语言检索设定信息
    ↓
AI 即时返回精准结果
    ↓
写作中如触发设定变更
    ↓
回到修改迭代阶段流程
```

## 七、用户审核清单（整合版）

在进入章节正文写作之前，用户做最后一次全局审核，对照以下清单：

**模块完整性**：
- 所有主要人物都有完整的 CHAR 档案（含情感身体词典和语气指纹）？
- 所有核心关系都有 REL 档案（含三层模型和变化曲线）？
- 所有主要人物都有 ARC 档案（含四节点和代价清单）？
- 所有势力都有 FAC 档案（含六项 DNA 编码和内部裂痕）？
- 所有势力对都有 FAC_REL 档案（含博弈矩阵和暗线）？
- 所有关键物品都有 ITEM 档案（含叙事功能和状态时间线）？

**交叉一致性**（AI 自动检查，用户确认结果）：
- 交叉验证报告中的「不一致」标记全部处理完毕？
- 每个角色的势力归属、物品持有、关系状态在档案和大纲之间完全对应？
- 弧线节点和大纲事件节点准确匹配？
- 物品的叙事功能在后续大纲中有对应的使用节点？

**联动更新**：
- 最近一次联动更新报告中的所有确认项已处理？
- 是否存在用户选择「暂不处理」的项目？如果存在，是否有明确的原因和后续计划？

**检索可用性**：
- 用户能否用自然语言在 10 秒内找到任何一个想要的设定信息？（测试：随机抽查三个设定点，用自然语言检索，看 AI 能否精准返回）

---

这套整合方案的核心思想：**用户不需要理解模块之间的依赖关系——AI 替你理解。用户不需要手动对比档案是否一致——AI 替你对比。用户不需要记住设定细节——AI 替你记，随时问随时答。** 用户唯一需要做的就是用自然语言发指令、做审核判断。
