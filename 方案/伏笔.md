前面把中央档案库的底层架构搭好了。伏笔追踪是这个架构下最考验系统严密性的模块——一个伏笔从埋下到回收可能横跨几十章，中间任何环节断裂，读者体验就崩了。

下面是一套完整的伏笔管理子系统。

---

## 一、伏笔的数据结构：让每个伏笔成为可追踪的实体

伏笔不是散落在章节里的注释，而是中央档案库中独立的结构化实体，拥有自己的 ID 和完整生命周期。

### 1.1 伏笔档案（FORE）

```  
id: FORE-XXX
type: 伏笔类型
status: 待埋设 | 已埋设 | 待回收 | 已回收 | 已废弃
plant_chapter: 埋设章节
plant_location: 埋设位置（章节内具体场景/段落）
plant_form: 埋设形式
reveal_chapter_planned: 计划回收章节
reveal_chapter_actual: 实际回收章节
reveal_form: 回收形式
payload: 伏笔承载的信息（真正要传达给读者的内容）
surface: 伏笔的表层呈现（读者第一眼看到的样子）
depth: 浅层 | 中层 | 深层
related_char: [CHAR-XXX, ...]
related_item: [ITEM-XXX, ...]
related_plot: [EVT-XXX, ...]
parent_fore: FORE-XXX 或 null（嵌套伏笔的上级伏笔）
child_fores: [FORE-XXX, ...]（嵌套伏笔的下级伏笔）
tags: [标签1, 标签2, ...]
created_at: 创建时间
last_modified: 最后修改时间
```

### 1.2 各字段详解

**type（伏笔类型）** 定义了伏笔在叙事中的功能角色：

| 类型 | 说明 | 例子 |
|------|------|------|
| 信息伏笔 | 提前透露一个信息碎片，回收时拼出全貌 | 第3章提到某历史事件的一个细节，第30章揭露事件全貌 |
| 人物伏笔 | 暗示人物的隐藏身份/能力/动机 | 「他从不碰银器」→ 第40章揭示他是狼人 |
| 物品伏笔 | 一个看似普通的物品，后续成为关键 | 第5章收到的无名礼物 → 第25章成为破解谜题的关键 |
| 能力伏笔 | 提前铺垫角色的某项能力 | 第8章随口提到会某种语言 → 第35章靠这个能力逃生 |
| 关系伏笔 | 暗示两个角色之间的隐藏关系 | 「他们看彼此的眼神不太对」 → 第50章揭示是失散兄妹 |
| 规则伏笔 | 暗示世界观的某个隐藏规则 | 反复出现的天气异常 → 第40章揭示世界的运行规则 |
| 情感伏笔 | 铺垫角色对某事的特殊情感反应 | 提到某个地名时角色表情变了 → 第28章揭示创伤来源 |
| 结构伏笔 | 叙事结构上的呼应（首尾呼应、镜像场景等） | 开场和结尾同一句对白，但含义完全不同 |

**depth（伏笔深度）** 决定了伏笔在被回收前对读者注意力的要求：

| 深度 | 读者感知 | 回收要求 | 跨度 |
|------|---------|---------|------|
| 浅层 | 大多数读者会注意到并记住 | 尽快回收 | 同卷内（1-10章） |
| 中层 | 细心读者会注意到 | 在读者快要忘记时回收 | 跨卷（10-30章） |
| 深层 | 几乎不会注意到，但潜意识会接收 | 回收时需要让读者回想起来 | 全书跨度（30章以上） |

**surface vs payload（表层 vs 载荷）** 是伏笔设计的核心。surface 是读者看到的，payload 是读者在回收时才真正理解的：

```
surface: 「他数了一下，盒子里还有六颗子弹。」
payload: 最后只剩一颗子弹时的抉择——「他想起那天盒子里的六颗子弹，
         现在只剩最后一颗。他从未想过，这最后一颗不是为敌人留的。」
```

### 1.3 伏笔密度等级

系统为每个章节自动计算伏笔密度：

```
伏笔密度 = 当前活跃伏笔数 / 章节长度（千字）
```

其中「活跃伏笔」= 已埋设但尚未回收的伏笔。设定阈值：

| 密度 | 等级 | 行动 |
|------|------|------|
| 0-1.5/千字 | 稀疏 | 可以继续埋设新伏笔 |
| 1.5-3.0/千字 | 适中 | 优先回收已有伏笔，谨慎埋新 |
| 3.0-5.0/千字 | 偏密 | 暂停新埋设，必须回收一些后再继续 |
| 5.0+/千字 | 过密 | 警告：读者可能无法追踪所有伏笔，强烈建议先回收 |

## 二、伏笔生命周期管理：从埋设到回收的完整追踪

### 2.1 四个状态的流转规则

```
待埋设 → 已埋设 → 待回收 → 已回收
                ↓          ↓
              已废弃     已废弃
```

**待埋设**：伏笔已创建，但尚未在正文中埋设。AI 在生成的章节细纲中会标注「本章需埋设 FORE-007」。

**已埋设**：伏笔已出现在正文中。系统自动记录埋设章节和具体位置。只允许埋设一次——如果用户试图再次埋设相同 payload，系统会警告：「FORE-007 已在第 N 章埋设，请勿重复埋设。如需多层次伏笔，请创建子伏笔。」

**待回收**：伏笔已经埋设，正在等待回收。这是最危险的阶段——长伏笔在这个阶段容易丢失。系统通过三种机制保证不丢失（见下文）。

**已回收**：伏笔已在正文中回收。系统自动记录回收章节和回收形式。只允许回收一次——如果用户试图再次回收同一个伏笔，系统会警告：「FORE-007 已在第 N 章回收，请勿重复回收。」

**已废弃**：伏笔因大纲调整而不再需要回收。废弃必须有明确的理由记录，不能悄悄消失。废弃的伏笔保留在档案中但不再参与活跃度计算。

### 2.2 长伏笔防丢失三机制

这是用户最关心的问题——跨几十章的长伏笔怎么保证不丢。

**机制一：活跃伏笔清单（每一章写作前自动提醒）**

当用户开始写第 N 章时，AI 自动输出当前所有活跃伏笔的状态：

```
📌 第 28 章活跃伏笔清单（共 7 个）

🔴 本回收窗口内（第 25-30 章），必须在本章或近期回收：
  FORE-003（中层-信息伏笔）| 第8章埋设 | 计划回收：第25-30章 | ⚠️迫近截止

🟡 中期待回收（第 31-50 章），暂不紧急但需保持存在感：
  FORE-007（中层-人物伏笔）| 第12章埋设 | 计划回收：第40章
  FORE-012（中层-规则伏笔）| 第18章埋设 | 计划回收：第45章
  FORE-015（深层-情绪伏笔）| 第5章埋设 | 计划回收：第48章

🟢 远期待回收（第 51 章以后），仅需偶尔在叙事中轻触维持记忆：
  FORE-022（深层-结构伏笔）| 第3章埋设 | 计划回收：第60章
  FORE-028（深层-关系伏笔）| 第10章埋设 | 计划回收：第55章

📊 本章伏笔密度：2.1/千字（适中）
建议：暂不埋新，优先考虑 FORE-003 的回收方案。
```

这个清单让长伏笔不可能「被遗忘」——每一章写作前，所有需要记住的伏笔都在眼前。

**机制二：伏笔遗忘预警**

当某个伏笔的「计划回收章节」已经过去 5 章以上仍未回收，系统发出预警：

```
⚠️ 伏笔遗忘预警

FORE-003（中层-信息伏笔）
  埋设：第8章
  计划回收：第25-28章
  当前章节：第35章
  状态：已逾期 7 章，仍未回收

建议行动：
  A. 在本章回收 FORE-003
  B. 调整计划回收章节到后续位置（需要确认新位置是否合理）
  C. 标记为已废弃（需要记录废弃原因）

请选择。
```

**机制三：伏笔密度曲线**

系统维护全书级别的伏笔密度曲线。用户可以在任何时候查看：

```
=== 伏笔密度曲线 ===

章节   活跃伏笔数   密度(/千字)   新埋设   已回收   状态
 1-5      3          1.2          3        0       ✅
 6-10     7          2.1          4        0       ✅  
11-15    12          3.5          5        0       ⚠️偏密
16-20    10          2.8          1        3       ✅
21-25    14          4.2          4        0       🔴过密
26-30     9          2.3          0        5       ✅
31-35     8          2.0          1        2       ✅
```

曲线告诉你三件事：
- 哪个区段新埋了太多伏笔但没有回收（21-25 → 26-30 的剧烈下降说明 26-30 回收了 5 个，但为什么要等到 26-30 才集中回收？为什么不提前分散？）
- 全书伏笔总数是否在可控范围内
- 是否存在伏笔「黑洞区」——很多伏笔埋了但从未回收的章节群

### 2.3 重复埋设和重复回收的拦截

这两个问题靠系统规则直接拦截，不需要用户记忆。

**重复埋设拦截**：

用户在写第 N 章时，如果正文中出现和某个已埋设伏笔高度相似的表层呈现（surface），AI 自动检测并警告：

```
⚠️ 疑似重复埋设

即将埋设的内容：「他握紧项链，指节发白——这是他母亲唯一留下的东西。」
已存在的伏笔：FORE-015（物品伏笔）
  埋设章节：第5章
  表层呈现：「他从抽屉最深处翻出那条褪色的银链，犹豫了很久才戴上。」
  
相似度：高。两个伏笔都围绕「母亲留下的饰品」展开。

判断：
  - 如果本章是故意呼应/强化 FORE-015 → 这是合法呼应，无需警告
  - 如果本章打算埋一个新伏笔 → 请创建新的 FORE，确保 payload 与 FORE-015 不同
  - 如果本章打算回收 FORE-015 → 请按回收流程处理

请确认意图。
```

**重复回收拦截**：

用户写回收场景时，如果试图回收一个已经标记为「已回收」的伏笔：

```
⚠️ 重复回收拦截

FORE-015（物品伏笔：「母亲的项链」）
  状态：已于第 42 章回收
  回收形式：项链内侧的刻字揭示了母亲的真实身份

你当前正在写的场景再次涉及该伏笔的回收。
如果这是进一步深化 → 请考虑是否需要创建 FORE-015 的子伏笔。
如果这是无意的重复 → 请删除此回收场景。

禁止直接将已回收伏笔再次作为新回收内容使用。
```

### 2.4 嵌套伏笔（多层次回收）

有些伏笔不是一次性回收的——第一层回收揭示一个信息，第二层回收揭示更深的信息。这种情况下不是「重复回收」，而是「嵌套伏笔」。

系统支持伏笔的父子关系：

```
FORE-010（父伏笔-深层）
  ├─ 埋设：第3章，看似普通的场景
  ├─ 第一层回收（第25章）：揭示这个场景其实是一个计划的开始
  │
  ├─ FORE-010-A（子伏笔-中层）
  │   ├─ 埋设：第26章，回收第一层时埋下的新疑点
  │   └─ 回收：第45章，揭示计划的真正目的
  │
  └─ FORE-010-B（子伏笔-深层）
      ├─ 埋设：第27章，回收第一层时不经意的另一个细节
      └─ 回收：第60章，揭示计划背后的隐藏操纵者（终极反转）
```

嵌套伏笔的规则：
- 每个子伏笔有自己独立的 FORE ID，独立追踪状态
- 子伏笔的 payload 必须和父伏笔的 payload 不同（不能是同一个信息的重复揭示）
- 子伏笔的回收必须在父伏笔的某一层回收之后
- 系统在父伏笔的所有子伏笔都回收后，自动将父伏笔标记为「已完全回收」

## 三、伏笔密度与节奏控制

### 3.1 全书伏笔预算

「伏笔预算」是全书允许的伏笔总量上限：

```
伏笔预算 = 全书预估章节数 × 每章平均伏笔活跃数目标（建议 1.8-2.5）
```

以一本 60 章的小说为例，按每章 2.0 个活跃伏笔计算，全书伏笔预算 ≈ 120 个伏笔-章（注意这是「伏笔数量 × 各伏笔活跃章数」的总和，不是伏笔个数）。

按深度分配预算：

| 深度 | 数量占比 | 平均活跃跨度 | 说明 |
|------|---------|-------------|------|
| 浅层 | 40% | 1-10 章 | 高频，快速回收，维持读者即时满足感 |
| 中层 | 35% | 10-30 章 | 中频，跨卷回收，形成中等叙事张力 |
| 深层 | 25% | 30+ 章 | 低频，全书跨度回收，形成全书级结构美感 |

### 3.2 每章伏笔密度自动检测

在用户生成章节细纲或正文时，AI 自动计算本章的伏笔密度并给出建议：

```
📊 第 28 章伏笔分析

当前活跃伏笔：9 个（浅层 2、中层 4、深层 3）
本章预计字数：4000 字
估算密度：2.25/千字（✅ 适中）

本章机会：
  - 可回收：FORE-003（浅层）、FORE-007（中层，接近截止）
  - 可埋设：最多 1 个新的中层伏笔

建议：本章优先回收 FORE-003 和 FORE-007，回收后密度降至 1.75/千字，
     届时可再埋 1 个新伏笔，为下一卷做铺垫。
```

### 3.3 伏笔类型分布的平衡

除了数量密度，还需要检查伏笔类型的分布。全是信息伏笔会让读者疲劳，全是物品伏笔会显得刻意：

```
=== 当前活跃伏笔类型分布 ===

信息伏笔 ████████░░ 4 个（40%）⚠️ 偏高
人物伏笔 ████░░░░░░ 2 个（20%）
物品伏笔 ████░░░░░░ 2 个（20%）
规则伏笔 ██░░░░░░░░ 1 个（10%）
情感伏笔 ██░░░░░░░░ 1 个（10%）
关系伏笔 ░░░░░░░░░░ 0 个 ⚠️ 缺失
结构伏笔 ░░░░░░░░░░ 0 个

建议：当前信息伏笔占比偏高，考虑将 1-2 个信息伏笔转化为人物或关系伏笔形式。
     同时关系伏笔完全空白，是否适合在当前章节埋设一个？
```

## 四、伏笔检索系统

### 4.1 多维度检索

用户在写作时可以按任何维度检索伏笔：

**按状态检索**：
> 「显示所有待回收的中层伏笔，按计划回收章节排序。」

**按关联实体检索**：
> 「CHAR-003 关联的所有伏笔，哪些还没回收？」

> 「涉及 ITEM-007 的所有伏笔，显示完整的埋设→计划回收→实际回收链条。」

**按章节范围检索**：
> 「第 30-40 章之间需要回收的伏笔有哪些？」

> 「第 5-15 章埋设的所有伏笔，哪些在第 50 章之后才回收？」

**按类型检索**：
> 「所有情感伏笔的密度分布——哪些卷/章集中了太多情感伏笔？」

**按状态异常检索**：
> 「所有逾期未回收的伏笔。」

> 「所有已废弃的伏笔及废弃原因。」

### 4.2 伏笔-章节对应表

系统自动维护一张伏笔与章节的完整对应表，用户随时查阅：

```
章节    埋设     回收     活跃数    活跃伏笔列表
 1     2        0        2        FORE-001, FORE-002
 2     3        0        5        FORE-001~005
 3     1        1        5        FORE-001~004, FORE-006
 4     0        0        5        FORE-001~004, FORE-006
 5     2        1        6        FORE-001~004, FORE-006, FORE-007~008
 ...
 25    1        3        4        FORE-006, FORE-012, FORE-015, FORE-016

```

这张表让用户一眼看到：哪些章节伏笔堆砌了，哪些章节伏笔空白了，以及全书最后一章活跃伏笔是否为 0（理想状态）。

### 4.3 回收率曲线

每一卷结束时，系统输出回收率报告：

```

第一卷回收：3 个（25%）—— 均为浅层伏笔，正常 ✅
遗留到第二卷：9 个（75%）
  中层：6 个（计划在第二卷内回收）
  深层：3 个（计划在第三卷回收）
  浅层：0 个 ✅（无浅层伏笔遗留，良好）

⚠️ 注意：有 2 个中层伏笔的计划回收章在第二卷前半段（第 16-20 章），
   建议在第二卷开始写作前先规划这两个的回收方案。
```

## 五、伏笔系统的实操集成

### 5.1 创建伏笔时

用户说：「我要在第 5 章埋一个伏笔——主角收到一封没有署名的信，不拆开。」

AI 自动执行：

```
✅ 伏笔创建完毕

FORE-015
  类型：物品/信息伏笔
  深度：中层
  表层呈现：主角收到一封没有署名的信，他把它塞进抽屉，没有拆开。
  载荷：待定（请指定这封信在回收时要透露什么信息？）
  埋设章节：第 5 章
  计划回收章节：待定（请指定计划在哪个章节回收？建议中层伏笔在埋设后 10-30 章回收）
  关联人物：CHAR-001（主角）
  关联物品：ITEM-XXX（信）

📊 第 5 章伏笔密度更新：当前 1.8/千字 → 埋设后 2.1/千字（✅ 仍适中）
```

### 5.2 回收伏笔时

用户在第 28 章写到回收场景时，AI 自动检测并确认：

```
检测到 FORE-015 的回收候选场景：
  「他颤抖着从抽屉最深处翻出那封积灰的信，信封上的字迹——他认出来了。」
```

## 六、总结：伏笔系统核心规则

| 问题 | 机制 | 保障效果 |
|------|------|---------|
| 长伏笔被遗忘 | 每章活跃伏笔清单 + 逾期预警 | 不可能遗忘——每章都在眼前 |
| 重复埋设 | 埋设时自动比对已有伏笔 surface，高相似度警告 | 系统拦截，用户确认意图 |
| 重复回收 | 回收时检查伏笔状态，已回收的直接拦截 | 系统硬拦截，不允许重复 |
| 伏笔密度失控 | 实时密度计算 + 阈值预警 + 全书预算 | 每章都知道当前密度是否健康 |
| 回收窗口过期 | 计划回收章节 ±5 触发预警 | 逾期无法忽视 |
| 类型分布失衡 | 类型占比统计 + 缺失类型提醒 | 避免全是信息伏笔 |
| 伏笔找不到 | 多维度检索系统 + 伏笔-章节对应表 | 任何维度秒级定位 |
| 全书收束不干净 | 终章活跃伏笔必须为 0 的硬约束 | 全书不能留悬案 |

伏笔管理的本质不是「记住」，而是「系统替你记住，并在关键时刻提醒你」。用户不需要记住第 8 章埋了什么、第 48 章该回收什么——系统在每一章开始前把这些信息直接推到眼前，用户只需要做创作判断。
