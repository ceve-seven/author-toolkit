小说档案和小说简介——这两个模块看起来简单，但做不好会很麻烦：小说档案容易变成「死档案」，创建完就再也没人看；小说简介则容易变成「一次性产品」，动笔前写了，写到一半小说走向全变了，简介还挂着旧内容。

下面分别设计。

---

## 一、小说档案：从静态备忘录到动态总控台

### 1.1 小说档案不是备忘录

传统认知里，小说档案就是一本笔记：记下书名、类型、一句话梗概、人物列表，然后就放在那里吃灰。但在这个 AI 协同系统里，小说档案应该是**所有模块的汇总视图**——它不是独立存储的数据，而是从中央档案库里**实时拉取**各模块的当前状态，拼成一张完整地图。

换句话说：小说档案不是「又一份数据」，而是「看数据的那个界面」。

### 1.2 小说档案的层级结构

小说档案分为三层，从宏观到微观：

**第一层：小说身份卡（元数据层）**

这一层回答「这是怎样一部小说」：

| 字段 | 说明 | 来源 |
|------|------|------|
| 书名 | 当前书名（可能是暂定名） | 用户输入 / AI 生成 |
| 副标题 | 如有 | 用户输入 / AI 生成 |
| 类型 | 主类型 + 子类型融合 | 灵感/主题模块 |
| 目标读者 | 年龄段、阅读偏好群体 | 灵感/主题模块 |
| 总字数预估 | 动态调整 | 根据当前大纲和已写章节实时估算 |
| 当前进度 | 已完成章节 / 总计划章节 | 实时计算 |
| 当前字数 | 已写正文的总字数 | 实时计算 |
| 创作状态 | 设定阶段 / 大纲阶段 / 初稿阶段 / 修改阶段 / 已定稿 | 用户手动切换，系统自动记录阶段切换时间 |
| 版本号 | 当前版本 | 每次重大修改后自动递增 |

**第二层：核心内容摘要（实时生成层）**

这一层的每个字段都不是用户手动填的，而是 AI 从各模块的当前状态中实时提取生成的：

| 字段 | 内容 | 生成方式 |
|------|------|---------|
| 一句话概括 | 当前主线的一句话总结 | AI 从大纲的主线冲突中提取 |
| 一段话梗概 | 约 200 字的剧情概要 | AI 从大纲的三幕结构中提取关键节点 |
| 主题陈述 | 这部小说在追问什么 | AI 从主题设定中提取 |
| 当前核心冲突 | 故事此刻的核心矛盾 | AI 从当前已写章节中提取最活跃的冲突线 |
| 主角当前状态 | CHAR-001 的弧线阶段、关系状态、持有物品 | 从 CHAR-001 档案实时拉取 |
| 关键人物数 | 当前活跃的主要人物数量 | 实时统计 |
| 势力格局简图 | 当前各势力关系和博弈状态 | 从 FAC_REL 档案实时提取 |
| 已埋未回收伏笔数 | 数字 + 列表链接 | 从 FORE 模块实时统计 |

**第三层：各模块快照（汇总视图层）**

这一层是其余各模块当前状态的汇总视图。不做重复存储，而是提供**快速预览和跳转入口**：

- 世界观规则列表（每条规则的摘要 + 状态）
- 人物列表（名字 + ID + 所属势力 + 弧线阶段）
- 势力列表（名字 + ID + 当前博弈地位）
- 物品列表（名字 + ID + 当前持有者 + 叙事功能）
- 大纲结构（卷/章树状图 + 完成状态标记）
- 伏笔统计（按状态分组的数量和列表）
- 最近 10 次变更记录

### 1.3 实时更新机制

小说档案的「实时更新」不依赖用户手动维护。当用户在其他模块做任何修改时，档案中对应的字段自动刷新：

```
用户修改了 CHAR-001 的 arc_id → 
  档案「主角当前状态」字段自动更新

用户完成第 28 章正文 → 
  档案「当前进度」「当前字数」自动更新
  「当前核心冲突」根据第 28 章内容重新提取

用户修改了大纲的主线 → 
  档案「一句话概括」「一段话梗概」自动重新生成

用户新增了一个 FORE → 
  档案「已埋未回收伏笔数」自动更新
```

用户不需要「打开小说档案更新一下」——它永远是最新状态，因为它的数据源是中央档案库，不是独立存储。

### 1.4 小说档案的输出格式

当用户需要输出档案时（比如发给编辑、合作者，或者自己阶段性回顾），AI 将上述三层内容排版为一份完整的档案文档。用户可以选择三种输出粒度：

- **完整版**：三层全部输出，包含各模块的详细数据
- **摘要版**：仅输出身份卡 + 核心内容摘要
- **投稿版**：仅输出适合发给出版方的信息（不包括设定细节和伏笔，避免泄底）

### 1.5 档案的阶段性检查功能

在每个创作阶段切换时（从设定阶段进入大纲阶段、从大纲阶段进入初稿阶段、从初稿阶段进入修改阶段），AI 自动对照档案做一次「阶段性准入检查」：

```
=== 阶段准入检查：设定阶段 → 大纲阶段 ===

✅ 世界观规则：已完成（8 条规则，五层审查通过）
✅ 人物设定：已完成（6 个主要人物，档案完整）
✅ 势力设定：已完成（4 个势力，DNA 编码完整）
✅ 势力关系：已完成（6 对势力关系，博弈矩阵完整）
✅ 人物关系：已完成（15 对人物关系，三维模型完整）
✅ 角色弧线：已完成（6 条弧线，四节点完整）
✅ 物品仓库：已完成（12 件关键物品，叙事功能标注完整）
✅ 主题设定：已完成（主题陈述 + 反向确认通过）
✅ 交叉验证：已完成（0 处不一致）

🎉 全部准入条件满足，可以进入大纲阶段。
```

任何一个模块不完整，准入检查就会标红并阻止进入下一阶段——防止「边写边补设定」导致的后期崩盘。

## 二、小说简介：从一次性文案到动态生成器

小说简介和小说档案的根本区别：档案是对内的（创作者自己看），简介是对外的（读者/平台/编辑看）。简介的核心矛盾是——它必须忠于小说的实际内容，但传统流程中简介写在最前面，写完才发现小说已经走样了。

### 2.1 简介不是一份，是一组

不同场景需要不同版本的简介。一个小说至少需要四套简介：

| 版本 | 场景 | 字数 | 核心任务 |
|------|------|------|---------|
| 一句话推荐 | 社交媒体转发、口播推荐、榜单 | 30-50 字 | 制造好奇，不解释，只诱惑 |
| 短简介 | 平台投稿页、APP 书城卡片 | 150-250 字 | 给出故事前提 + 核心冲突 + 一个钩子 |
| 标准简介 | 书籍详情页、封底、豆瓣 | 300-500 字 | 展开世界观 + 人物 + 冲突 + 情感赌注 + 钩子 |
| 长简介 | 编辑沟通、版权推荐、书评参考 | 800-1500 字 | 完整交代故事前提、人物弧线预告、主题暗示、但不泄底 |

每一套简介的结构不同：

**一句话推荐的结构**：

```
[异常情境] + [情感赌注]

例：「一个靠记忆当货币的世界里，有个女孩正在遗忘所有人——包括她自己。
     但她决定在被彻底清空之前，找出是谁偷走了她的记忆。」
```

**短简介的结构**（四段式，每段 1-2 句）：

```
第1段：世界的异常点（这个世界和我们的世界有什么不同？为什么有趣？）
第2段：主角的困境（她是谁？她卡在什么矛盾里？）
第3段：冲突升级（什么事件打破了平衡？她不得不做什么？）
第4段：情感钩子（如果她失败/成功，什么将永远改变？）
```

**标准简介的结构**（在短简介基础上扩展）：

```
第1段：世界观引入（比短简介多一层细节，让读者「看见」这个世界）
第2段：主角深度介绍（不止困境，还有她的欲望、伤口、矛盾）
第3段：核心冲突展开（对手是谁？冲突为什么不可调和？）
第4段：情感赌注（不止是外在目标，更是内在代价）
第5段：开放式钩子（一句让人不得不翻开的结尾）
```

### 2.2 简介的实时更新机制

简介的核心问题不是「怎么写」，而是「怎么保证简介和小说始终匹配」。

**触发更新的条件**：

以下任何情况发生，AI 自动标记简介为「可能需要更新」状态：

- 大纲主线发生结构性变化（比如核心冲突换了）
- 主角的人物设定发生重大变化（比如核心欲望改了）
- 世界观的核心规则被修改或新增
- 章节写作进度超过简介生成时预估的「简介覆盖范围」
- 势力格局发生重大变化（如果简介中涉及势力关系的话）

用户不需要猜——AI 在每次修改后自动比对当前简介内容和各模块当前状态，如果发现不一致，直接提示：

```
⚠️ 简介可能过时

检测到以下变更可能影响当前简介：
  - CHAR-001 的核心欲望从「复仇」改为「寻找真相」（标准简介第 2 段需要修改）
  - 世界观规则 RULE-003 新增了「时间瘟疫」设定（短简介第 1 段可能需要补充）

建议：重新生成简介的所有版本，或仅修改受影响的版本。
```

**动态重新生成，不是手动修改**：

用户不需要逐字修改简介。简介的生成逻辑是结构化的——每个段落的生成提示词指向特定的数据源。当数据源变了，AI 重新执行生成，输出新版简介：

```
简介生成数据源映射：

一句话推荐：
  → 来源：主题陈述 + CHAR-001 的核心矛盾 + 世界观最吸引人的一个异常点

短简介第 1 段（世界异常点）：
  → 来源：世界观规则中最具叙事张力的 1-2 条规则

短简介第 2 段（主角困境）：
  → 来源：CHAR-001 的核心欲望 + 核心恐惧 + 弧线起点状态

短简介第 3 段（冲突升级）：
  → 来源：大纲主线冲突 + 主角弧线的催化节点 + 主要对手设定

短简介第 4 段（情感钩子）：
  → 来源：主角弧线的终点状态 + 主题的核心追问

标准简介各段：在短简介的基础上，加入更多数据源的细节
长简介：在前两者基础上，加入支线冲突、关键配角、势力博弈简况
```

这样保证了简介的「完美适配」——它永远从当前小说的实际数据中提取生成，不是一份独立存在、需要手动维护的文本。

### 2.3 简介的 A/B 版本管理

用户对简介的判断是主观的——同一个数据源可以生成多个不同调性的简介。系统支持 A/B 版本并存：

- **A 版（悬念版）**：信息公开较少，强调未知和好奇
- **B 版（设定版）**：信息公开较多，强调世界观的独特性和人物魅力
- **C 版（情感版）**：关注点放在人物的情感困境上，用情感共鸣吸引读者

用户切换版本，AI 用同一份数据源、不同的生成策略（信息隐藏程度不同、侧重点不同）重新生成。所有版本都挂在中央档案库的简介模块下，用户可以随时对比、选用、或让 AI 混合两个版本的特质生成新版本。

### 2.4 简介的禁忌规则（硬约束）

简介虽然由 AI 生成，但必须遵守以下硬约束，用户可以在生成时选择开启或关闭某一项：

| 约束 | 说明 | 默认状态 |
|------|------|---------|
| 不泄底 | 不透露第三幕的核心反转 | ✅ 开启 |
| 不剧透人物结局 | 不透露任何角色的最终命运 | ✅ 开启 |
| 不透露伏笔载荷 | 可以暗示伏笔的存在，但不揭示载荷内容 | ✅ 开启 |
| 不超过指定字数 | 严格控制在场景要求的字数内 | ✅ 开启 |
| 不虚假宣传 | 简介中暗示的内容必须在大纲中有对应 | ✅ 开启 |

最后一条「不虚假宣传」是 AI 简介最常见的坑——简介写了一个精彩的前提，但大纲里根本找不到对应的内容。系统通过「简介内容 → 大纲交叉验证」来拦截：

```
简介声称：「她必须在七天内找到凶手，否则全城的人都会死。」

AI 在大纲中检索：是否存在「七天时间限制」的机制？是否存在「全城人死亡」的危机节点？
如果不存在 → 标记为「虚假宣传」，提示用户修改简介或补充大纲。
```

### 2.5 简介的更新频率策略

不是每次修改都需要提醒更新简介。系统根据变更的影响级别决定提示频率：

| 影响级别 | 变更类型 | 提示策略 |
|---------|---------|---------|
| 高 | 主线冲突改变、主角核心设定改变、世界观核心规则改变 | 立即提示，强烈建议更新 |
| 中 | 配角设定改变、势力格局改变、大纲节点移动 | 标记为待更新，用户查看简介时提示 |
| 低 | 物品状态改变、单章细节修改、伏笔状态变化 | 不提示，但下次手动生成时自动使用最新数据 |

## 三、小说档案与小说简介的联动

档案和简介之间的联动关系：

```
        中央档案库（唯一数据源）
              ↓
    ┌─────────┴─────────┐
    ↓                   ↓
小说档案              小说简介
（内部全量视图）      （外部精简输出）
    ↓                   ↓
各模块实时汇总      结构化提取 + 文学生成
    ↓                   ↓
创作者决策参考      读者/平台触达
```

两者共享同一数据源，但输出完全不同：
- 档案追求**完整性**——不遗漏，不美化
- 简介追求**吸引力**——在忠于数据的前提下做文学性包装

当数据源更新时，两者同时受益——档案的对应字段自动刷新，简介被标记为待更新并提示用户。

## 四、实操指令集

**小说档案操作指令**：

> 「打开小说档案。」→ AI 输出当前完整档案（摘要版默认，可指定版本）

> 「输出投稿版档案。」→ AI 输出适合发给出版方的版本

> 「阶段准入检查。」→ AI 对照所有模块做完整性检查

> 「查看最近 10 次变更记录。」→ AI 从变更日志中提取

**小说简介操作指令**：

> 「生成全部四套简介。」→ AI 输出一句话/短/标准/长简介

> 「生成悬念版短简介。」→ AI 用悬念策略生成短简介

> 「重新生成标准简介，侧重情感线。」→ AI 调整生成策略

> 「检查简介是否过期。」→ AI 比对简介和当前数据源

> 「更新所有版本简介。」→ AI 逐版本重新生成，输出新旧对比

> 「简介交叉验证——检查有没有写了但大纲没有的内容。」→ AI 逐条比对

> 「给我三个版本的短简介，我挑一个。」→ AI 输出 A/B/C 三个版本
