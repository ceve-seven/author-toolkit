前面所有模块的设计——人物、势力、物品、伏笔、细纲、正文约束——都依赖一个共同的底层：中央档案库。如果这个底层只是「把所有文件放在一个文件夹里」，那前面的联动更新、交叉验证、约束拉取全都跑不起来。

这一轮把中央档案库从抽象概念变成可操作的系统设计。

---

## 一、中央档案库是什么

它不是文件夹，不是文档集合，不是项目管理工具。它是一套**结构化数据系统**，每一个创作元素（人物、势力、物品、伏笔、章节等）在其中都是一个**拥有唯一 ID、结构化字段、双向引用关系、变更日志、版本快照的数据实体**。

它和传统「创作文件夹」的根本区别：

| 维度 | 传统文件夹 | 中央档案库 |
|------|-----------|-----------|
| 数据形式 | 自由文本（docx、txt、笔记） | 结构化字段 + 自由文本混合 |
| 元素标识 | 靠文件名和用户记忆 | 靠唯一 ID，系统自动追踪 |
| 引用关系 | 用户手动记住「A 和 B 有关」 | 系统自动维护引用图 |
| 修改影响 | 改了 A，手动去改 B、C、D | 改了 A，系统自动追踪影响范围 |
| 检索方式 | 关键词搜索或翻文件 | 字段级精确查询 + 语义检索 |
| 版本管理 | 用户手动另存为 | 自动版本快照 + 可回滚 |

### 2.2 补充说明：不在档案库里的东西

以下内容**不**存于中央档案库，而是作为临时输出或用户本地文件存在：

- AI 生成的灵感建议（用户选择后，选定的才入库）
- 章节正文的中间草稿（只有定稿入库，中间版本由版本快照覆盖）
- 网络搜索的外部参考资料（用户选择保存的才入库）
- 对话历史中的临时讨论（除非用户明确要求存档到某个模块）

## 三、目录架构：物理结构与逻辑视图分离

### 3.1 对用户可见的逻辑视图

用户看到的不是物理文件路径，而是逻辑目录——通过「小说档案」界面（之前讨论过）来浏览和访问：

```
用户视角（通过小说档案界面访问）：

我的小说：《XXX》
  ├── 📊 总览面板（进度/状态/变更日志/最近的审查报告）
  ├── 🎯 主题与灵感
  ├── 🌍 世界观（8 个子维度可展开）
  ├── 🏛️ 势力与势力关系
  ├── 👤 人物（展开为人物列表，点击进入完整档案）
  ├── 🔗 人物关系（关系网络图或列表视图）
  ├── 📈 角色弧线
  ├── 🎒 物品仓库
  ├── 🔮 伏笔管理
  ├── 📐 结构（分卷/大纲/细纲/关键剧情/节奏曲线）
  └── 📖 正文（按卷/章浏览）
```

用户不需要知道文件存在哪里、格式是什么——就像用 Notion 一样，看到的是结构化页面。

### 3.3 数据文件的标准格式

每个实体的 JSON 文件遵循统一的结构：

```json
{
  "id": "CHAR-001",
  "type": "character",
  "version": 17,
  "created_at": "2026-05-01T10:00:00",
  "last_modified": "2026-05-27T15:30:00",
  "modification_history": [
    {"version": 16, "timestamp": "2026-05-25T...", "change_summary": "调整核心欲望"},
    {"version": 17, "timestamp": "2026-05-27T...", "change_summary": "更新faction_id"}
  ],
  
  "fields": {
    "name": "主角姓名",
    "faction_id": "FAC-003",
    "items_held": ["ITEM-005", "ITEM-012"],
    "arc_id": "ARC-001",
    "core_contradiction": "...",
    "emotional_body_map": {
      "恐惧": "指尖发冷，肩胛骨收紧",
      "愤怒": "下颌肌肉跳动，声音变低而不是变高"
    },
    "voice_fingerprint": {
      "vocabulary_pool": ["具体名词为主", "回避抽象形容词"],
      "sentence_preference": "主谓结构为主，短句",
      "forbidden_expressions": ["突然意识到", "不知为何", "莫名其妙地"],
      "verbal_tics": {"短语": "行吧", "频率": "每2-3章出现1次"}
    },
    "knowledge_boundary": {
      "chapter_1": {"known": [...], "unknown": [...], "misconception": [...]},
      "chapter_28": {"known": [...], "unknown": [...], "misconception": [...]}
    },
    "perception_filter": "他首先注意到的是空间中的「缺口」——少了什么，而非多了什么",
    "status_timeline": [
      {"chapter": 27, "physical": "左臂受伤（未愈）", "emotional": "对CHAR-002的信任正在瓦解"}
    ]
  },
  
  "references": {
    "referenced_by": ["REL-001", "REL-003", "ARC-001", "FORE-003", "FORE-007", "FORE-031"],
    "references_to": ["FAC-003", "ITEM-005", "ITEM-012", "ARC-001"]
  }
}
```

格式要点：
- `id`、`type`、`version` 是每个实体的必选元数据字段
- `modification_history` 记录每次修改的版本号和摘要（不存完整旧数据——旧数据由 snapshots 目录负责）
- `fields` 是模块特定的业务数据
- `references` 是双向引用关系——这是精确拉取和联动更新的核心

## 四、怎么做到精确拉取需要的数据

### 4.1 三级索引体系

精确拉取不靠全文搜索（慢且不准），靠三级索引：

**一级索引：实体索引（entity_index.json）**

ID → 物理路径的映射，O(1) 查找：

```json
{
  "CHAR-001": "modules/characters/CHAR-001.json",
  "FAC-003": "modules/factions/FAC-003.json",
  "ITEM-005": "modules/items/ITEM-005.json",
  "FORE-003": "modules/foreshadows/FORE-003.json",
  "CH-028": "structure/chapter_outlines/CH-028_outline.json"
}
```

当约束文件需要读取 CHAR-001 的 knowledge_boundary 中第 28 章的数据时，检索路径是：

```
"CHAR-001 第28章的知识边界"
  → entity_index → CHAR-001.json 路径
  → 读取 fields.knowledge_boundary.chapter_28
  → 返回精确数据
```

不需要全文搜索，不需要读取整个文件再筛选。字段级直达。

**二级索引：引用关系图（reference_graph.json）**

记录了「谁引用了谁」和「谁被谁引用」——这是联动更新的核心：

```json
{
  "CHAR-001": {
    "references_to": ["FAC-003", "ITEM-005", "ITEM-012", "ARC-001"],
    "referenced_by": ["REL-001", "REL-003", "REL-005", "ARC-001", "FORE-003", "FORE-007", "FORE-015", "FORE-031"]
  },
  "FAC-003": {
    "references_to": ["RULE-002", "RULE-005", "LOC-003"],
    "referenced_by": ["CHAR-001", "CHAR-005", "CHAR-008", "FAC_REL-001", "FAC_REL-003"]
  }
}
```

当用户修改了 FAC-003 的某个核心字段时，系统不需要扫描全库——直接从引用关系图中取出 `referenced_by` 列表，这就是全部受影响实体的清单。

**三级索引：章节-实体映射（chapter_entity_map.json）**

按章节维度组织的反向索引——「第 N 章涉及哪些实体」和「实体 X 出现在哪些章节」：

```json
{
  "by_chapter": {
    "28": {
      "characters": ["CHAR-001", "CHAR-003", "CHAR-006"],
      "items_in_use": ["ITEM-005", "ITEM-007", "ITEM-012"],
      "foreshadows_plant": ["FORE-031"],
      "foreshadows_reveal": ["FORE-003"],
      "foreshadows_touch": ["FORE-007", "FORE-015"],
      "locations": ["LOC-003"],
      "factions_referenced": ["FAC-003", "FAC-005"]
    }
  },
  "by_entity": {
    "CHAR-001": [1, 2, 3, 5, 8, 12, 15, 18, 22, 25, 27, 28],
    "ITEM-005": [5, 8, 12, 18, 22, 25, 26, 28]
  }
}
```

这个索引让「生成第 28 章约束文件」变成一次精确的索引查询而非全库扫描：

```
步骤1：查 chapter_entity_map → 第 28 章的实体清单
步骤2：查 entity_index → 每个实体的文件路径
步骤3：并行读取所有实体文件 → 提取第 28 章相关的字段
步骤4：编译为约束文件
```

全程不需要全文搜索。每一步都是 O(1) 或 O(n) 的精确查询，n = 该章节涉及的实体数量（通常 10-25 个）。

### 4.2 字段级查询

除了「拉取某个实体的全部数据」，系统支持字段级查询——只取需要的字段，不加载整个文件：

```
查询：「CHAR-001 在第 28 章的 physical 状态」
  → 路径：CHAR-001.json → fields.status_timeline → 筛选 chapter=28 → 取 physical
  → 返回：「左臂受伤（未愈）」

查询：「所有在 28-35 章需要回收的伏笔」
  → 路径：chapter_entity_map → by_chapter 中 28-35 章 → 取 foreshadows_reveal
  → 去重 → 查 FORE 档案 → 筛选 status=待回收
  → 返回：FORE-003, FORE-007, FORE-012 的摘要

查询：「第 28 章中 CHAR-001 不应该知道的信息」
  → 路径：CHAR-001.json → fields.knowledge_boundary.chapter_28 → unknown
  → 返回：["FAC-004 的参与", "CHAR-002 的真实身份"]
```

### 4.3 语义检索（辅助方式）

当用户用自然语言查询而非精确字段名时，系统降级为语义检索：

> 「找所有和主角有关联但还没翻脸的角色。」

系统的处理流程是：
1. 语义解析：「主角」= CHAR-001，「有关联」= 在 REL 档案中出现，「没翻脸」= actual_layer 不是敌对/决裂
2. 翻译为结构化查询：查 CHAR-001 的 referenced_by 中 type=relation 的实体 → 逐条检查 actual_layer
3. 返回结果

语义检索是精确查询的入口层——最终还是要落到结构化查询上。纯粹靠向量相似度的模糊匹配在小说设定管理中是危险的（「翻脸」可能匹配到「脸色变了」这种不相关的描写）。

## 五、怎么保证与现有进度同步且不影响其他模块

### 5.1 同步机制：变更日志驱动的增量同步

中央档案库不是定期全量同步，而是基于**变更日志的增量同步**。任何模块的数据变更，都会在 `change_log.jsonl` 中追加一条记录：

```json
{"timestamp": "2026-05-28T15:30:00", "entity": "CHAR-001", "field": "faction_id", 
 "old_value": "FAC-003", "new_value": "FAC-005", "version": 18,
 "triggered_by": "用户手动修改"}
```

同步的具体含义取决于场景：

**场景一：约束文件生成**
约束文件是「在生成那一刻」从档案库中拉取的快照。它永远是最新数据，不需要同步——因为它直接从源头读取。

**场景二：正文写作中途设定被修改**
用户在写第 28 章的过程中修改了 CHAR-001 的设定。此时：

1. 变更日志记录修改
2. 系统检查：第 28 章是否已经生成了部分场景？
3. 如果场景一已完成但场景二未开始 → 在生成场景二时自动使用新的设定数据
4. 如果场景一已完成且引用了被修改的设定 → AI 检查旧设定在场景一中的呈现是否需要修正
5. 如果需要修正 → 生成《场景一设定修正建议》，用户确认后执行局部修改

```
⚠️ 设定变更影响检测

CHAR-001 的 faction_id 已从 FAC-003 改为 FAC-005。

第 28 章场景一（已完成）影响检查：
  - 场景一中 CHAR-001 在 FAC-003 的仓库中发现痕迹——这个场景本身不依赖 CHAR-001
    的所属势力。场景的物理地点（FAC-003 仓库）不受 CHAR-001 的 faction_id 影响。
    ✅ 场景一无需修改。
  
  但注意：如果场景一中 CHAR-001 使用了 FAC-003 成员的内部知识或权限来进入仓库，
  则这个前提不再成立。当前场景一中 CHAR-001 是通过跟踪 CHAR-002 进入仓库的——
  不依赖势力身份。✅

第 28 章场景二（未生成）：
  将使用新的 faction_id（FAC-005）拉取约束。
```

**场景三：多个模块被同一变更影响**
修改 FAC-003 的核心规则 → 变更日志记录 → 系统从 reference_graph 中取出所有 referenced_by 实体 → 生成《联动更新报告》→ 用户逐条确认 → 系统批量更新受影响实体的版本号。

整个过程通过变更日志串联，每个模块的版本号独立递增。同步不是「覆盖」，而是「追溯影响范围 + 用户确认 + 批量更新」。

### 5.2 隔离机制：模块间通过 ID 引用而非数据复制

隔离的核心原则：**任何模块都不存储其他模块的数据副本，只存储 ID 引用。**

错误做法（数据复制）：
```json
// CHAR-001.json 中错误地复制了 FAC-003 的数据
{
  "faction": {
    "name": "黎明会",
    "goal": "推翻现有秩序",
    "leader": "某某"
  }
}
```
→ FAC-003 的目标改了，CHAR-001 里的副本不会自动更新 → 数据不一致。

正确做法（ID 引用）：
```json
// CHAR-001.json 中只存储 ID
{
  "faction_id": "FAC-003"
}
```
→ FAC-003 的目标改了，CHAR-001 不需要更新。当需要显示「CHAR-001 所属势力的目标」时，实时从 FAC-003 拉取。

这就是为什么约束文件需要在生成时「拉取」数据——它把分布在各个模块中的设定，在生成那一刻聚合为一份完整约束。生成之后就过期了（下次生成时重新拉取），所以不存在「同步」问题。

### 5.3 进度同步

「进度」在中央档案库中不是一个独立的模块数据，而是一组衍生指标：

- `当前章节` = STRUCTURE 模块中已标记为「已完成」的最大章节号
- `当前字数` = MANUSCRIPT 模块中所有已完成章节的字数总和
- `当前阶段` = META 模块中的 `创作状态` 字段（用户手动切换）
- `活跃伏笔数` = FORE 模块中 status=已埋设 的伏笔数量

这些指标不需要同步——它们是实时从各模块计算出来的。用户在任何时候打开「小说档案」面板，看到的进度数据都是从各模块拉取的当前状态。

## 六、怎么搜集需要的内容

### 6.1 搜集时机：不是等用户问，是主动搜集 + 用户确认

中央档案库的内容搜集分两个阶段：

**初始创建阶段**：用户和 AI 对话，逐模块创建内容。每创建一个实体，自动入库并分配 ID、建立引用关系。

**写作迭代阶段**：在正文写作过程中，AI 自动识别需要补充的设定：

```
在生成第 28 章场景一时，发现 CHAR-006 正在执行「第 27 章策划的计划」，
但 FAC-006（CHAR-006 所属势力）的档案中缺少「第 27 章策划的计划」的具体内容。

⚠️ 设定缺口检测

FAC-006 的档案中缺少以下信息：
  - 第 27 章策划的「计划」的具体内容（目前只有一句描述性提及）
  - 该计划与 FAC-006 的核心目标之间的逻辑关系

建议：在继续写作前，补充 FAC-006 的这一段设定。
暂时跳过也可以——CHAR-006 在本章只是警告者，不直接执行计划。

补充设定 / 暂时跳过？
```

### 6.2 搜集方式

**方式一：用户主动输入**

用户在任何时候可以说：

> 「给 CHAR-004 补充感知过滤器。」→ AI 根据已有的人物设定生成候选，用户确认后入库

> 「添加一个新物品 ITEM-015，功能是……」→ AI 生成完整物品档案，用户确认后入库

**方式二：AI 从正文中反向提取**

写完一章正文后，AI 自动扫描正文中出现的「新设定元素」——正文中提到了但档案库中没有记录的内容：

```
=== 第 28 章新设定元素扫描 ===

疑似新设定：
  1. CHAR-006 提到的「北境的旧实验室」—— LOC 档案中无此地点。
     → 这是一个新地点还是临时的对话细节？
        如果是新地点 → 创建 LOC-XXX 档案
        如果是临时细节 → 在对话上下文中标记，不作为正式设定

  2. CHAR-003 在场景二中对他住所的描述方式——「他选择住在这里是因为
     这是他唯一看不到 FAC-003 总部的地方」。
     → CHAR-003 档案中缺乏「与 FAC-003 的空间关系」信息。
     → 建议补充 CHAR-003 的 perception_filter 或 status_timeline 中的相关条目。

请逐条确认是否入库。
```

**方式三：跨模块关联扫描**

当用户补充了一个模块的设定后，AI 自动扫描其他模块中可能需要关联更新但尚未关联的缺口：

```
CHAR-003 的 past_trauma 字段新增：「曾在 FAC-003 的地下室被关押三天」。

跨模块影响扫描：
  → FAC-003 档案中是否需要补充「地下室」作为地点子项？ 目前 FAC-003 只有「总部大楼」。
  → CHAR-003 与 CHAR-001 的关系（REL-003）——CHAR-001 是否知道这件事？
     如果不知道，这是未来关系发展的一个潜在炸弹，建议在 REL-003 的 hidden_layer 中记录。
  → CHAR-003 的弧线（ARC-003）——这个创伤是否已反映在弧线节点中？
     ARC-003 的催化节点目前是「外部事件」，如果这个创伤是内在驱动，
     建议考虑是否需要调整为「内在创伤被外部事件触发」的复合催化。

请确认需要补充哪些？
```

### 6.3 搜集的质量控制

不是所有内容都值得入库。入库有门槛：

| 内容类型 | 入库标准 | 不入库处理 |
|---------|---------|-----------|
| 新人物 | 在 3 个以上章节中出现，或在关键剧情中发挥作用 | 临时标记为「待观察」，2 卷内未达标则丢弃 |
| 新地点 | 被 2 个以上场景使用，或承载关键事件 | 作为临时细节保留在对应章节的注释中 |
| 新物品 | 具有叙事功能（不只是场景道具） | 不单独建档，仅在场景描述中存在 |
| 新世界观规则 | 影响至少 1 个人物的行为选择或 1 个情节的可行性 | 作为假设保留，用户确认后入库 |
| 新势力 | 影响势力博弈格局，或与现有人物/情节有关联 | 不单独建档 |

这个门槛阻止了档案库膨胀——不是每一个路人的名字都需要建档。

## 七、构建路径：从零到完整档案库

### 7.1 构建顺序

中央档案库的构建不是一次性全部完成，而是按创作阶段逐步填充：

```
阶段一：种子孵化期
  → 创建 META（小说身份卡）
  → 创建 THEME（主题陈述 + 反向确认）

阶段二：设定搭建期
  → 创建 WORLD（世界观规则 → 地理 → 历史 → 社会 → 政治 → 经济 → 文化 → 技术）
  → 创建 FACTION（势力档案 → 势力关系）
  → 创建 CHARACTER（人物档案 → 情感身体词典 → 语气指纹 → 感知过滤器）
  → 创建 RELATION（人物关系对 + change_curve）
  → 创建 ARC（角色弧线，在 RELATION 完成后基于关系网络设计）
  → 创建 ITEM（物品仓库，在 CHARACTER 和 FACTION 完成后基于持有关系创建）

阶段三：大纲规划期
  → 创建 STRUCTURE（分卷 → 大纲主线 → 大纲支线 → 关键剧情标注 → 节奏曲线）

阶段四：逐章写作期
  → 逐章创建 MANUSCRIPT（约束文件 → 正文 → 审查报告）
  → 同步更新 CHARACTER（status_timeline, knowledge_boundary）
  → 同步更新 ITEM（holder_timeline, status_timeline）
  → 同步更新 FORE（plant/reveal 状态变更）
  → 同步更新 RELATION（change_curve 新节点）
```

每个阶段的模块创建完成后，运行一次交叉验证，确保引用完整性。

### 7.2 初始创建的指令

用户不需要手动操作目录和 JSON 文件。以下指令驱动 AI 完成初始构建：

```
阶段一：
「创建小说身份卡。」→ AI 询问关键信息 → 生成 META 模块

阶段二（按顺序，每一步审核后继续下一步）：
「创建世界观规则。」→ AI 生成 RULE 档案 → 用户审核
「运行规则自洽审查。」→ AI 原子化 + 交叉推演 → 修补裂缝
「创建势力。」→ AI 基于世界观生成 FAC 档案 → 用户审核
「创建势力关系。」→ AI 生成博弈矩阵 → 用户审核
「创建人物。」→ AI 基于势力 + 世界观生成 CHAR 档案（含情感身体词典/语气指纹/感知过滤器）
「创建人物关系。」→ AI 基于人物档案生成 REL 档案（含三维模型/change_curve）
「创建角色弧线。」→ AI 基于人物档案 + 关系网络生成 ARC 档案
「创建物品仓库。」→ AI 基于世界观规则 + 人物 + 势力生成 ITEM 档案

阶段三：
「生成分卷配置。」→ AI 分析弧线节点 → 识别分卷边界
「生成大纲。」→ AI 基于全部设定生成三幕/四幕结构
「标记关键剧情。」→ AI 按八条标准标注关键剧情章
「生成节奏曲线。」→ AI 输出全书冲突强度分布

阶段四：
从第 1 章开始逐章生成。
```

## 八、总结

| 问题 | 核心方案 |
|------|---------|
| 档案库包含什么 | 12 大模块，每个创作元素是拥有 ID、结构化字段、双向引用、变更日志的数据实体 |
| 怎么构建 | 按创作阶段逐步填充，每个模块通过 AI 生成 + 用户审核 + 交叉验证的方式入库 |
| 目录架构 | 物理文件按模块/实体组织；用户看到的是逻辑视图（通过小说档案面板访问） |
| 精确拉取 | 三级索引（实体索引→引用关系图→章节实体映射）+ 字段级查询，O(1) 定位 |
| 进度同步 | 基于变更日志的增量同步；模块间仅存 ID 引用不存数据副本；进度指标实时计算 |
| 内容搜集 | 初始创建（逐模块生成）+ 写作中发现缺口（自动检测新设定/跨模块关联）+ 入库门槛控制 |
